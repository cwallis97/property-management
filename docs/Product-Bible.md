# Product Bible – Version 2.0

**Status: Version 2.0 is the current, authoritative product direction.** It supersedes Version 1.0 in every place the two disagree — most notably on primary beachhead market and on the core experience model. Version 1.0 content is preserved below, under its own section, for historical context and because much of its product detail (asset fields, work order fields, document types, etc.) still stands and is not restated twice.

Working Title: PropertyOS (Placeholder)

## Purpose

PropertyOS is the operating system for the physical property.

We are not building another property management software like Entrata, AppFolio, or Yardi. We are building the software owners, regional managers, maintenance directors, and property managers open every morning to understand the health of every property they own.

## Primary Beachhead

**Manufactured-housing / mobile-home communities.**

This supersedes Version 1.0's framing, which listed general property management companies as primary and mobile home parks as a future/secondary market. Manufactured housing is now the entry wedge, not an eventual expansion.

## Architecture Principle

**Manufactured-housing-first UX, property-type-neutral engine.**

The product is designed and tested against manufactured-housing communities first, but nothing in the schema or logic may be specific to that property type. The underlying engine must support apartments, hotels, commercial properties, and any other property type without code changes — only through the generic `Property → Location → Asset` hierarchy. Manufactured-housing-first shapes *design decisions and defaults*, not the data model.

This is the specific case of a broader rule: **specialize the experience, generalize the engine.** Any given screen may be designed and tuned around one persona or one property type's real workflow — a technician reporting a water break, a manufactured-housing manager reviewing sewer spend — but the schema underneath must never encode that specialization. If a feature needs a property-type-specific column or a persona-specific table, that's a signal the design belongs one layer up, in UX, not in the data model.

## Core Operational Graph

PropertyOS is one connected operational graph. Dashboard, Property, Map, Locations, Assets, Work Orders, Costs, and Reports are not separate modules — they are different interfaces onto the same underlying records. **Build one graph, then provide different views and workflows over that graph.**

```
Property
  → Site Plan (uploaded spatial reference layer)
  → Location (self-referential hierarchy — Lot, Building, Floor, Unit, Suite, ...)
  → Asset
  → Work Order
      → Location / Asset (optional context, not required for either)
      → Map Position (mapX, mapY — a normalized point on the Property's Site Plan)
      → Category → Work Type (stable reference identity, not free text)
      → Cost Entries (itemized, dated by when the expense was incurred)
      → Notes / status history (completion never deletes it)

Cost Entries → Reports (spend grouped by Category → Work Type → Work Order, reconciling at every level)
```

Every real capability above operates on these same records — there is no parallel "reporting truth" or "map truth" that duplicates a Work Order, a cost, or a position. A dollar shown in a report, a marker shown on a map, and a row shown in a Work Order list must all trace back to the identical underlying row.

**Connected architecture does not mean every future capability must be implemented immediately.** The graph is deliberately built to extend cleanly — new node types and new relationships can be added later — without meaning those extensions exist today. See "Current Implementation State" below for what is actually built versus what remains roadmap.

## Spatial Operations Principle

PropertyOS preserves **where** every physical maintenance event happened, then connects that spatial history to **what** happened, **when** it happened, **what asset/location was involved**, **what it cost**, and **how often similar events have occurred**.

Site Map, Work Orders, Assets, Costs, and Reports must operate on the same underlying operational records rather than becoming separate feature silos. The uploaded site plan is the spatial reference layer — the base canvas every physical position is expressed relative to. Work Orders represent events that happen on that physical property and may carry an exact normalized map position. Assets represent physical things that may occupy positions on that property. Future infrastructure layers represent physical systems (water, sewer, electrical, roads) laid over the same canvas. Reports will analyze this same operational history — spatial position is preserved from the moment an event is recorded so future reporting can answer questions like "where is this money/activity going?" without re-deriving location after the fact.

Spatial position and organizational hierarchy (Location) are related but distinct concepts. A Work Order's map position must never be forced to align with a Location assignment merely to satisfy schema, and a Location must never be assigned to a Work Order merely because it needs coordinates. Physical truth is preserved exactly as recorded; hierarchy context is layered on top only when genuinely useful. PropertyOS shows *where* work occurred — it does not claim causation merely because events cluster spatially.

## Work Order Completion & History Principle

Completion removes work from the active operational queue; it never removes the maintenance event from PropertyOS operational history. Completed Work Orders remain permanently accessible for historical review, reopening, future Reports, future cost analysis, future spatial/map history, and recurring-problem analysis. PropertyOS never deletes a completed Work Order — completion is a status change, not a removal. Views that default to showing active operations (the Dashboard, a property's default Work Orders list, the default Property Map) exclude completed work so they stay focused on what needs attention right now, but that same completed history remains one filter away, in full, forever.

## Maintenance Classification & Cost History Principle

Every physical maintenance event should carry a structured Category (Water, Sewer, Electrical, Roads, Concrete, Trees/Landscaping, Buildings/Facilities, General/Other) and, where known, a Work Type identifying the specific operation performed within that Category (e.g. Sewer → Line Cleaning vs. Sewer → Main Repair). Work Types are stable, reference-identified records, not free text — a Work Order stores a reference to a Work Type's identity, never a typed string, so a later rename of that Work Type's display label instantly and correctly updates how every historical Work Order referencing it is shown, with nothing to rewrite. Categories and Work Types exist to make PropertyOS's operational history reliably groupable — "all Sewer Work Orders" or "all Line Cleaning Work Orders" must be an exact, trustworthy query, never a text search.

A Work Order's actual cost is built from itemized cost entries (labor, materials, vendor, equipment, other), each independently timestamped and attributable, entered incrementally over the Work Order's life — while work is underway, at completion, or afterward by an authorized manager. Total cost is always derived by summing those entries, never stored as a separate number a user must keep in sync by hand. Neither classification nor cost is required to complete a Work Order — completion and financial reconciliation are related but separate concerns, and invoices or internal labor costs legitimately arrive after the work itself is done. Completed Work Orders remain fully editable for classification and cost exactly as they remain accessible for everything else in PropertyOS's operational history.

Every cost entry carries its own **costDate** — the calendar day the expense was actually incurred, distinct from the entry's system-entry timestamp (when it was typed into PropertyOS, which may be days or weeks later). Maintenance Spend reporting is always dated by costDate, never by a Work Order's creation date, completion date, or a cost entry's own creation timestamp — those answer "when was this recorded," not "which period does this money belong to."

## Maintenance Spend Reporting Principle

Reports are derived from the same operational records Work Orders and the Property Map already use — a dollar shown in a report always traces back to a real Work Order and its real cost entries; there is no separate reporting truth. Maintenance Spend includes recorded cost entries regardless of whether their parent Work Order is still active or already completed: a cost entry is a real recorded amount the moment it exists, and Work Order status answers a different question (is the work done) than cost entries do (what has been spent). An open Work Order with real recorded costs contributes those dollars to spend for whichever period(s) its cost entries' costDate values fall into, exactly as a completed one would.

"Average Cost / Work Order" is always computed over Work Orders that have at least one recorded cost entry in the current scope — a Work Order with no recorded cost is absent from that calculation, never treated as a $0 data point that would silently pull the average down. Every ranked breakdown (by Category, by Work Type) must reconcile exactly against the summary total above it, including an explicit "Uncategorized" bucket for spend on Work Orders that haven't been classified yet — no dollar is ever silently dropped from a breakdown just because it lacks a category or Work Type.

## Current Implementation State

The sections above describe the connected model PropertyOS is built toward. This section states plainly what already exists in the running product versus what remains roadmap, so the graph's connectedness is never mistaken for the graph's completeness. Update this section as capabilities actually ship — do not mark something built until it is.

**Built and real, operating on the graph above:**

- **Property, Location** — the full property-type-neutral engine, with company-scoped multi-tenancy.
- **Asset** — structured `operational`/`needs-attention`/`critical` status; a real Asset Detail page (Property/Location/Category context, its active Work Orders, and its full maintenance history including completed Work Orders); a portfolio-wide Assets view (All/Needs Attention/Critical, Property filter) alongside the property-scoped one. **Lifetime Maintenance Spend and every history row's cost are always computed fresh from that Asset's real Work Orders and Cost Entries — never a stored total on the Asset record.**
- **Work Order** — full status lifecycle (open, assigned, in_progress, waiting, completed), Active / Completed / All views, completion and reopening, all preserving full history.
- **Work Order Notes** — append-only update history; never deleted, even after completion.
- **Site Plan** — customer-uploaded (PDF/PNG/JPG), the spatial reference layer a Property's Work Orders position themselves against.
- **Work Order map position** (`mapX`/`mapY`) — both **Report Issue** (map-first) and **Mark Location on Map** (Work-Order-first) write to the same Work Order record; there is no separate spatial record.
- **Category** — a small validated set of values directly on the Work Order.
- **Work Type** — a normalized, stable-identity reference table (not free text). Global/shared taxonomy today, with a reserved column for future company-specific types.
- **Cost Entries** — itemized, each carrying its own `costDate`; a Work Order's cost is always derived by summing its entries, never stored separately.
- **Reports V1 (Maintenance Spend)** — company-scoped SQL aggregation, Category → Work Type → Work Order drill-down, date-range and property filters, values that reconcile exactly at every level.
- **Reports → Map** ("View on Map") — at the Work Order drill level, with a single property selected, view that report's matching Work Orders spatially on the property's Site Plan. Reuses the same Work Order records, `mapX`/`mapY`, and `spendInPeriod` already used elsewhere; unmapped Work Orders remain fully counted in every report total.
- **Vendor** — a real, Company-scoped entity (contact info, service/category, Active/Inactive status), distinct from the pre-existing `vendor` Cost Entry *type* (that label still just means "external/contracted expense"; it never identified who). A Vendor's participation in Work Orders and its attributable spend are two deliberately separate relationships: which Work Orders a Vendor has worked (a join, tracking the currently-assigned Vendor without ever discarding past assignments) versus which specific Cost Entries actually paid that Vendor (an explicit, optional link on the Cost Entry itself). Actual Vendor Spend is never inferred from a Work Order's total cost — only from Cost Entries genuinely attributed to that Vendor. Properties Worked, Work Order count, Actual Spend, and Most Recent Work are all derived fresh, never stored on the Vendor. Reassigning or deactivating a Vendor never removes or alters its historical participation, cost attribution, or Work History — only Active/Inactive changes whether it's offered for new assignments.
- **Document V1** — operational files (Warranty, Invoice/Receipt, Inspection, Permit, Estimate/Bid, Manual, Vendor/Compliance, Other) attaching to exactly one of Property, Asset, Work Order, or Vendor — enforced by a database constraint, not just application logic (Location attachment deferred). A portfolio-wide Documents page (search, category filter, Active/Archived) and a shared "Documents" section embedded in Property/Asset/Work Order/Vendor Detail, both reading the same records. Company ownership is direct and validated server-side on every read and write; Property context shown for an Asset/Work Order-attached Document is always resolved at read time, never stored redundantly. Archiving is a one-way soft-delete — the underlying file is preserved, never deleted, except when a Document's file is deliberately replaced by a new upload. **Production-storage requirement:** Documents currently store files on local disk behind an isolated `documentStorage.js` module, acceptable for development only — real customer Document uploads must not go live in a production deployment until that module is backed by persistent, non-ephemeral storage.
- **Company-level role authorization (Roles & Permissions V1)** — three operational roles (Admin, Manager, Technician; `owner` is treated identically to Admin) enforced through a centralized, code-defined **ROLE → CAPABILITY** map (`server/authorization/capabilities.js`, mirrored for UI purposes in `client/src/utils/capabilities.js`), not scattered `if (role === "admin")` checks. Every mutation endpoint (Property lifecycle, Location, Asset, Work Order, Work Order Notes/Costs, Vendor, Document, Site Plan upload) independently re-derives the caller's role from their own server-side Membership and rejects unauthorized attempts with a 403, regardless of what a client claims — frontend hiding is UX only, never the authorization boundary. Admin holds every capability, including Company/Property administration (creating Properties, archiving/restoring them, Settings access). Manager holds the same day-to-day operational capabilities as Admin minus that administration. **Technician's role-level capability set remains the empty set** — this map is unchanged by Technician Work Order Actions V1 (below); a Technician's narrow, resource-scoped execution rights on their own assigned Work Orders come from a deliberately separate authorization axis, never from widening this map. Settings → Properties is gated behind the same Admin-only capability at the route level.
- **Settings → Users & Roles V1** — a real, working member list and role editor, gated behind a dedicated `users.manage` capability (Admin/Owner only). `GET /api/members` lists the caller's Company (Membership id, user id, name, email, role, and — since Property Access V1 below — `accessMode`/`propertyIds`); `PUT /api/members/:id` changes a member's role among Admin/Manager/Technician. `owner` is visible but never editable through this endpoint (no ownership transfer exists — the schema has no separate "primary owner" flag beyond the role itself, so treating that role as immutable is the smallest rule that can never leave a Company without one), and a caller can never change their own role, avoiding an accidental Settings lockout mid-session. Both protections are enforced server-side, not just hidden in the UI. This answers only "what can this member do" — "where can they do it" is Property Access V1's concern, documented separately below.
- **Invitations V1** — a real second person can now join an existing Company. A persisted `Invitation` record (Company, invited email, role, an unguessable one-time token, expiration, `invitedByUserId`, and nullable `acceptedAt`/`revokedAt` — "pending" is derived from those three, never a separately-stored status) is preferred over a stateless signed token specifically for one-time redemption, expiration, and cancellation all being plain columns rather than claims baked into a token. Only Admin/Owner may create, list, or revoke invitations (`users.manage`), restricted to Admin/Manager/Technician as the invited role — never `owner`. Creation rejects an already-a-member email and a duplicate still-pending invite for the same email. The Admin-facing UI generates a copyable `/join/<token>` link; there is no automated email delivery (the project has no email-sending infrastructure, and none was added). Redemption (`POST /api/invites/token/:token/accept`) runs under a new, deliberately narrower `requireFirebaseUser` middleware — same Firebase-token verification as `requireAuth`, but no Company auto-provisioning — so a brand-new invitee never gets a throwaway Company created for them before joining the one they were actually invited to; `requireAuth`'s existing behavior for every other route is unchanged. Company and role are read exclusively from the stored invitation, never from the redeeming client; the authenticated email must match the invited email; expired, revoked, or already-accepted invitations are all rejected with distinct messages; redeeming while already a member of that Company creates no duplicate Membership. Since Property Access V1 below, invite creation may optionally include `propertyIds` (Manager/Technician only — never Admin, who is always unrestricted); the invited access is stored on the `Invitation` row and only ever applied once, at acceptance, after re-validating every id against the inviting Company (an id that's no longer valid by then fails the acceptance outright rather than silently granting All Properties).

- **Settings Completion V1** — Settings now has exactly four sections, all real: Properties, Users & Roles, Organization, Account. **Organization** exposes the one Company field that's actually editable — `name` — via `PUT /api/companies/:id`, gated by the same `settings.access` capability Property administration already uses (no new capability introduced). **Account** lets every member, regardless of role, edit their own `displayName` via `PUT /api/users/me` — deliberately capability-free, since it's inherently self-scoped (no id parameter exists or is accepted; it can only ever touch the caller's own row) rather than an administrative action. Email/Role/Organization are shown read-only there: email is kept in sync with the Firebase token by `requireAuth` on every request (so editing it here would just be overwritten), and role/Company membership are exclusively Users & Roles' concern. `displayName`, by contrast, is written once from Firebase at account creation and never re-synced afterward, so a change made through Account persists correctly and is never silently overwritten by a later login. Settings' route is no longer wrapped in a blanket Admin/Owner capability gate — it now needs to be reachable by every authenticated member for Account's sake, with Properties/Users & Roles/Organization each gating their own section individually exactly as Users & Roles already did.
- **Appearance preference** — a System/Light/Dark selector lives in Account, backed by `ThemeContext` and persisted to `localStorage` only (no `User` column, no migration — deliberately device-local; a preference set on one device does not follow the member to another). "System" tracks `prefers-color-scheme` live via a `matchMedia` listener. A small inline script in `index.html` stamps `data-theme` on `<html>` synchronously before React paints, avoiding a flash of the wrong theme.
- **Dark Mode V1** — the application is fully visually themed for the resolved System/Light/Dark preference above, not just state/plumbing. `index.css` defines a small semantic token layer (`--color-page/surface/surface-subtle/line/line-strong/ink/ink-secondary/ink-muted/accent/accent-hover/accent-ink`, ~11 tokens total) as CSS custom properties, redefined under `:root[data-theme="dark"]`; a Tailwind v4 `@custom-variant dark` repoints the `dark:` utility variant at that same attribute instead of the OS media query, so the app's own preference — not just the OS's — governs every themed surface. Structural chrome (page/card backgrounds, borders, dividers, primary/secondary/muted text, primary-action buttons and their inverted-lightness accent chip, focus rings, inputs) is driven entirely by these tokens; status/priority colors (red/amber/emerald/blue/purple badges and inline destructive/confirmation text) stay as literal Tailwind utility classes with explicit `dark:` variants at each call site, since their meaning is semantic (severity), not structural. Coverage is application-wide: shell/navigation (Sidebar, Header, mobile tab fallback), Dashboard, Portfolio, Property/Asset/Vendor/Work Order Detail, all tables (Asset/WorkOrder/Vendor/Document), every modal (create/edit for Property, Location, Asset, Work Order, Vendor, Document, Invite), Settings (all four sections), and shared primitives (EmptyState, SectionSpinner, PageHeader, Breadcrumb, SearchableSelect). The Site Plan/document canvas's own toolbar and surrounding frame are themed; the uploaded site-plan image or PDF content itself is never recolored (an intentionally white site plan stays white in Dark Mode, exactly as a real uploaded document would), and its on-image marker dots keep their fixed literal colors since they're read against that unchanging bitmap, not the app chrome. Login and Signup are a deliberate exception: their existing animated-gradient design predates and is independent of the gray-scale theme system, so they do not participate in System/Light/Dark and always render their fixed brand treatment.

- **Property Access V1 (Step 1 — security/data-model/configuration only)** — a real, enforced answer to "which Properties may this member see/operate within," layered inside the Company boundary (which remains the hard tenant/security boundary, unchanged) and independent of role/capability (which still answers only "what may they do"). `Membership.accessMode` (`all` | `restricted`, default `all`) is the explicit, never-inferred switch — a `PropertyAccess` row (`membershipId`, `propertyId`, both `ON DELETE CASCADE`, unique per pair) is only ever created for and consulted by a `restricted` Membership; an `all` Membership has none and none are checked. Owner and Admin are always `accessMode = all` and cannot be restricted, enforced server-side regardless of what a client sends; promoting a Membership to Admin automatically resets it to `all` and clears any stale grants. Manager and Technician default to `all` (today's unchanged behavior for every existing Membership — the column default *is* the entire backward-compatibility strategy, no backfill needed) and may be switched to `restricted` by an Admin/Owner from Settings → Users & Roles, via a single-purpose "Property access" modal (All Properties / Selected Properties, the latter showing every Property including archived ones so an existing grant to an archived Property is never accidentally dropped by an unrelated edit). `restricted` with zero selected Properties is rejected outright, both in the UI and server-side — a member with zero accessible Properties has no real V1 use case and would be a silent full lockout. An Admin/Owner can never restrict their own access or an Owner's/Admin's. `getAccessiblePropertyIds(req, companyId)` (`server/authorization/propertyAccess.js`) is the single reusable helper every enforcement point calls — `null` means unrestricted (zero extra queries, since `accessMode` is already present on the `req.memberships` rows `requireAuth` loads for every request), a real array means restricted. Enforcement covers every Property-owned read and write: Property (list/get/update/archive/restore), Location, Asset, Work Order (including Cost Entries and Notes, both inheriting through Work Order → Property), Site Plan, Dashboard's aggregate summary, Reports' Maintenance Spend (both the totals/breakdown and an explicit request for an inaccessible `propertyId`, which fails with a clear error rather than a silently-empty result), and Documents attached to a Property/Asset/Work Order (deriving access through that attachment's own Property relationship). An inaccessible-but-in-Company resource still 404s, never 403s, preserving the existing non-enumerating convention. Two Company-level exceptions, both deliberate: the Vendor directory itself (name/contact/category) stays fully visible to every member regardless of restriction — only a Vendor's derived aggregates (Actual Spend, Work Order history, Properties Worked) are scoped down to accessible Properties for a restricted member — and Vendor-attached Documents stay Company-level/always visible, since a Vendor isn't Property-owned. `GET /api/members` now returns `accessMode` and (when restricted) the granted `propertyIds`; `PUT /api/members/:id/property-access` is the management endpoint, gated by the same `users.manage` capability, replacing a restricted Membership's grants atomically (delete-then-recreate in one transaction) rather than diffing. **What Property Access V1 explicitly does NOT include:** Work Order Assignment — a deliberately separate milestone, now built; see its own entry below.

- **Property Scope Unification V1 (Step 2)** — one coherent mental model, replacing the previous page-by-page inconsistency (a mix of live-follow, one-time-seed-then-diverge, and unrelated-reset behaviors that predated Property Access existing at all). **Property Access** (above) answers *which* Properties a member may reach — enforced entirely server-side, unchanged by anything below. **Property Scope** (the Sidebar's sessionStorage-backed selector, `PropertyScopeContext`) is purely the UX lens for *which accessible Property the member is currently focused on* — never itself a source of authorization. Its option list is exactly `GET /api/properties`' (already access-restricted, active-only) response, so an inaccessible or archived Property can never appear as a choice; "All Properties" means all Properties the member can access, not literally every Property in the Company. Dashboard, Portfolio, Assets, Work Orders, Documents, and Reports all **live-follow** scope — there is no page-specific exception — changing it while any of those pages is mounted re-filters immediately, with no remount or re-navigation, because each reads `scopePropertyId` straight from context rather than seeding a local copy that could drift. The page-local "Property" dropdowns that Assets, Work Orders, Documents, and Reports each used to maintain independently (Dashboard and Portfolio never had their own) were removed outright as redundant with the Sidebar's always-visible selector, not converted into a second control that writes back to it — one dropdown, one source of truth. Work Orders' "Needs attention" summary strip and Assets'/Work Orders' table density (whether a Property column is worth showing) both now also key off scope, so nothing on those pages can disagree with what the table beneath it actually contains. Reports keeps this same rule but adds one wrinkle: because a Category/Work Type drill-down is only meaningful within the Property context it was drilled into, an actual scope *change* while Reports is mounted resets the drill back to its root breakdown (the same reset `goToRoot()` already performs for a manual breadcrumb click) — but the initial mount, including restoring a real "back from a Work Order" navigation, is never affected by that reset, so back-navigation still lands exactly where the user left. **Property Detail** remains the one writer — visiting `/portfolio/:propertyId` sets scope to that Property, unconditionally overwriting whatever was previously selected, and an inaccessible Property already fails safely (404 from the server, rendered as its existing "not found" empty state, which never calls the scope-setter). **Portfolio composes scope on top of its own existing Active/Archived/All lifecycle filter**, client-side, with no second API call: the already access-restricted, already lifecycle-filtered list `getProperties({status: view})` returns is narrowed to the one scoped Property when scope is set, or left as the full accessible list when scope is "All Properties" — the exact same rule every other page follows, no exception, no banner (an earlier version of this milestone gave Portfolio a permanent exception plus an explanatory banner; both were removed once Portfolio was brought in line with the rest of the app, since a page-specific exception is confusing regardless of how well it's explained). Portfolio's page description reflects scope the same way Dashboard's already does (the scoped Property's name, or "All properties across your organization" when unscoped). **The Sidebar's own "Portfolio" nav link is scope-aware**: with "All Properties" selected it points at `/portfolio` (the directory); with a specific Property selected it points directly at that Property's own Detail page (`/portfolio/:id`), skipping the redundant one-row directory a scoped visit to `/portfolio` would otherwise show. Its active-highlighting is independent of that destination — it lights up for the whole `/portfolio` URL space regardless of current scope, so it can never appear unselected while the user is genuinely on a Portfolio-family page. **Changing scope while already on a Property's Detail page now acts as a context switch**: selecting a different Property navigates straight to that Property's Detail page, and clearing to "All Properties" navigates to the Portfolio directory — both using a history *replace*, not a push, since this is a side effect of the global selector rather than a deliberate click, so the browser Back button returns to wherever the user was before landing on that Property rather than bouncing through every Property the selector passed through. **Stale/invalid scope recovery** lives in one place, `Sidebar.jsx`'s `PropertyScopeSelector` — a `propertiesLoaded` flag distinguishes "the accessible-Properties fetch hasn't resolved yet" (must not clear scope, or every fresh page load would flash-clear a valid selection) from "it resolved and the previously-selected Property genuinely isn't in that list anymore" (archived, deleted, or access revoked — including down to zero accessible Properties), and only the latter clears scope safely to "All Properties." The same guard that lets an archived-but-still-accessible Property's own Detail page stay unfought is unchanged. The global "Add Document" modal's Property picker (used when opened from the portfolio-wide Documents page, where the target entity isn't yet implicit) preselects the current scope when it's a valid option, without hiding the picker or making the choice ambiguous.

- **Work Order Assignment / My Work V1** — a fourth, distinct concept alongside the three above: **Company Membership** (tenant identity), **Property Access** (which Properties a member may operate within), and **Property Scope** (the UX lens across accessible Properties) are joined by **Work Order Assignment** — operational responsibility assigned to one specific *person* for one individual Work Order, answering "whose is this," never "what may they do" (that's still role/capability) and never "where may they operate" (that's still Property Access). `WorkOrder.assignedMembershipId` (nullable, `ON DELETE SET NULL`) references `Membership`, not `User` — assignment is inherently Company-scoped by construction, the same reasoning `PropertyAccess.membershipId` already established. Assignment is always to the specific person, never their role: the UI shows "Assigned to: Mike Johnson," never "Assigned to: Technician," and if that person's role later changes, the Work Order stays assigned to them. **Assignment never grants Property Access** — a valid assignee must already belong to the Work Order's Company and already have Property Access to its Property (`membershipHasPropertyAccess`, the symmetric counterpart to `getAccessiblePropertyIds`/`requirePropertyAccess`: those answer "can the caller reach this Property," this answers "can this other Membership reach it," same underlying `PropertyAccess` data, not a second authorization model). Assignment changes are gated by the same `workOrder.edit` capability (and the same `requirePropertyAccess` check) `updateWorkOrder` already enforces for every other field — no new capability, and **Technician's zero-mutation-capability stance from Roles & Permissions V1 is deliberately unchanged**: a Technician may see Work Orders assigned to them (via My Work, if they otherwise have Property Access) but cannot assign/reassign/clear an assignment, nor does being assigned grant them any new edit capability. `GET /api/work-orders/:id/assignable-members` is a new, narrow, Work-Order-scoped read (same tenant/Property-Access resolution `getWorkOrder` uses, gated on `workOrder.edit`) returning only `{membershipId, name}` for Company members who actually have Property Access to that Work Order's Property — deliberately not a reuse of `GET /api/members` (gated on `users.manage`, a capability Manager doesn't hold, and carrying far more than a picker needs). Work Order detail/update/company-list/property-list responses all carry the same minimal `assignee: {membershipId, name} | null` shape. **My Work has no dedicated endpoint** — it's the existing portfolio-wide Work Order list, filtered client-side by the caller's own Membership id (exposed via a new `companies[].membershipId` on `/api/users/me`, self-referential and never another member's), the exact same pattern Property Scope's own client-side filtering already uses; never a browser-supplied id. In the Work Orders page, "My Work" is a peer view alongside Active/Completed/All (`My Work | Active | Completed | All`), not a second axis or a separate status lifecycle — it shows every status assigned to the caller, composes automatically with Property Scope (a specific Property narrows My Work to that Property; "All Properties" means all accessible), and defaults to off (Active stays the default view). **If an assignee later loses Property Access, the assignment is deliberately left untouched** (`assignedMembershipId` is never auto-cleared) — their own reads of that Work Order (including My Work) simply stop returning it, purely as an emergent property of Property Access already being re-evaluated on every request; an authorized Manager/Admin can still see the stale assignee's name and manually reassign or clear it. No general audit/history system exists yet (see Roadmap) — this milestone doesn't add a one-off audit table for assignment changes, but nothing about its design (a plain FK column, changed via the same `updateWorkOrder` mutation boundary everything else already goes through) would need rework when one is eventually added.

- **Technician Work Order Actions V1** — a fifth, distinct concept layered on top of the four above: **Company Membership** (tenant identity), **Role/Capability** (broad permission tier), **Property Access** (where a member may operate), and **Work Order Assignment** (which specific person owns a Work Order) are joined by **Technician Work Order Actions** — narrow, resource-scoped execution rights limited to a person's own currently-assigned, currently-accessible, not-yet-completed Work Order. **This is deliberately not `workOrder.edit`.** Technician's entry in `ROLE_CAPABILITIES` is still the empty set (see Roles & Permissions V1, above) — granting broad `workOrder.edit` to Technician was explicitly rejected in favor of a third, independent authorization axis answering a narrower question neither the role/capability map nor Property Access can express: "may THIS caller perform THIS specific mutation on THIS specific Work Order, right now." That axis is `server/authorization/workOrderActions.js` — a small, centralized policy module (`WORK_ORDER_ACTIONS`, `canPerformWorkOrderAction`/`requireWorkOrderAction`), not a generic policy framework, mirroring the existing `requireCapability`/`requirePropertyAccess` inline-guard shape so call sites read the same way. It grants exactly two paths to "allowed": (1) full editor — the caller holds the endpoint's normal capability (`workOrder.edit`/`workOrderNote.create`/`workOrderCost.create`) for the Work Order's Company, completely unchanged from before this milestone; or (2) assigned Technician — `workOrder.assignedMembershipId` equals the caller's own Membership id *for that Work Order's Company specifically* (never a bare `User` id, never an arbitrary/first entry in a multi-company caller's Membership array — the identical `req.memberships.find(m => m.companyId === companyId)` idiom `getRoleForCompany`/`getAccessiblePropertyIds` already use), the Work Order is not `completed`, and the requested action is in the narrow assignee allowlist (`status`, `note.create`, `cost.create` — nothing else). Property Access is deliberately **not** re-checked inside this module; every call site already runs `requirePropertyAccess` before reaching it, so "AND Property Access" is satisfied by call-order, not re-implemented — the same invariant Work Order Assignment V1 already relied on for its own Option A revocation behavior. **Field-level enforcement, not just endpoint-level:** `updateWorkOrder` previously gated its entire body behind one `workOrder.edit` check; a non-full-editor now must submit *only* `{ status }` — any other key present anywhere in the body (assignment, Vendor, priority, due date, Location/Asset, title/description/category, or any other scalar) causes the **entire request** to be rejected with a 403, never partially applied and never silently dropped, so a crafted payload mixing one allowed field with one forbidden field cannot smuggle the forbidden one through. `createWorkOrderNote`/`createWorkOrderCost` each swap their single `requireCapability` line for `requireWorkOrderAction` with no other change — Notes remain append-only and Cost Entries remain create-only for every role (no edit/delete surface exists anywhere in this codebase, so "Technician can't edit/delete" is true by construction, not by an added check). `archiveWorkOrder` and `GET /api/work-orders/:id/assignable-members` are untouched — both remain `workOrder.edit`-only, so Technician can never archive or self-assign/reassign/clear an assignment. **Completion ends Technician mutation rights** — evaluated against the Work Order's current, freshly-queried status on every request, never cached: a Technician may mark their own assigned Work Order Completed (the pre-request state isn't completed yet), but once it is, all three assignee actions stop immediately, including status changes — Reopen remains, as before, `workOrder.edit`-only, so Technician cannot reopen. Reassignment or Property Access revocation likewise take effect on the very next request with no extra bookkeeping, for the same reason Work Order Assignment V1's own revocation behavior needed none: every check re-reads current database state. **Frontend**: no separate Technician page — `WorkOrderDetail` derives `isAssigneeActor` (`!canEditWorkOrder && assignee is caller && not completed`) and widens exactly three existing conditions (the inline Status picker, the Notes composer, the Add Cost button) to `existingCondition || isAssigneeActor`; Assignee, Vendor, and Description stay gated on `canEditWorkOrder` alone, so Technician never sees those as interactive regardless of assignment. This is UX convenience only — the server independently re-derives and enforces the identical rule on every request.

- **Generalized Audit / Event History V1** — a sixth, distinct concept layered on top of the five above: **Company Membership**, **Role/Capability**, **Property Access**, **Property Scope**, **Work Order Assignment**, and **Technician Work Order Actions** now all feed one generalized, append-only change history rather than each mutation being visible only in its own row's current state. This directly **supports SOC 2 readiness** and is a **near-term control foundation** — it is explicitly not, by itself, SOC 2 compliance, which also depends on organizational process, policy, infrastructure, vendor management, incident response, and access-review controls outside this feature. A new `audit_events` table (model `AuditEvent`, `server/models/AuditEvent.js`) holds one row per server-recorded, semantically-meaningful mutation — deliberately **not** event sourcing, a generic per-column diff log, or a Sequelize global hook: every row is written by an explicit call from inside the specific controller that already validated and performed the underlying business mutation, at `server/services/auditService.js#recordAuditEvent`, which makes no authorization decisions of its own and never accepts a raw request body — every call site hand-picks the exact minimal fields it records. **V1 instruments exactly eight events**: `work_order.assignment_changed`, `work_order.status_changed`, `work_order.note_created`, `work_order.cost_created`, `membership.role_changed`, `membership.property_access_changed`, `property.archived`, `property.restored`. Broad Work Order scalar edits, Asset/Location/Vendor/Document/Site Plan mutations, Company rename, and Invitation lifecycle changes are deliberately **not** instrumented in V1 (Invitations already carry their own complete lifecycle columns — `invitedByUserId`/`acceptedAt`/`revokedAt` — making a second audit entry redundant, not valuable) — these remain explicit Audit V2 candidates, not an oversight. **Atomicity**: every one of the eight events commits in the *same* database transaction as the business mutation it describes (reusing this codebase's existing `sequelize.transaction` pattern, first established in `membershipController.js`) — if the `AuditEvent` insert fails, the whole request fails and the business mutation rolls back too, so the app can never silently succeed at a mutation it claims to audit while actually losing the audit row. `updateWorkOrder` can legitimately emit up to two events (assignment AND status) from a single authorized request when both fields genuinely change; the `WorkOrderVendor` current-link swap remains its own separate, pre-existing, non-transactional step, unaffected by this milestone (Vendor changes are not an audited V1 event). **No-op suppression**: resubmitting an unchanged value (same status, same assignee, same role, same Property Access set) creates no row — an audit trail's value is signal, not noise. **Actor model**: `actorMembershipId`/`actorUserId` are normalized, nullable (`ON DELETE SET NULL`) references, resolved via `resolveActor(req, companyId)` using the exact `req.memberships.find(m => m.companyId === companyId)` idiom `getRoleForCompany`/`callerMembershipId` already established — never a bare `User` id, never an arbitrary/first Membership for a multi-company caller, and never anything client-supplied. Alongside those references, `actorRole`/`actorName`/`actorEmail` are **point-in-time snapshots**, captured once at write time, so a Membership later promoted/demoted or a User later renamed never rewrites what an old event already says happened; `actorName`/`actorEmail` are nullable (a future non-human/system actor need not have either). For the three events reachable through Technician Work Order Actions' two authorization tiers (`work_order.status_changed`, `work_order.note_created`, `work_order.cost_created`), `metadata.authorizationPath` records `"full_editor"` or `"assigned_technician"` — separate from `actorRole`, and never exposing anything more of the internal capability/policy implementation than that one semantic value. **Target model**: a generalized `entityType` + `entityId` pair (`entity_type` validated against an app-level `ENTITY_TYPES` list, deliberately **no DB CHECK constraint** — unlike `entityType`'s small set today, it's expected to grow with every future audit milestone, and a CHECK would mean a migration per new type; `entity_id` deliberately carries no physical FK, an accepted trade-off of the generalized model over one nullable FK column per entity type) plus an `entityLabel` point-in-time snapshot (e.g. the Work Order title or Property name at event time) — never re-resolved live, so a later rename or even permanent deletion of the target never changes what the event already says. `propertyId` stays a first-class, real, indexed FK column (`ON DELETE SET NULL`, unlike Document's own `RESTRICT` on the same column — an AuditEvent's meaning doesn't depend on its Property still existing the way a Document's does) specifically because every Property-owned V1 event needs it for scoped filtering, and a future Property-Access-scoped read view can reuse it with zero schema change. **Company boundary**: `companyId` is `ON DELETE RESTRICT` (deliberately unlike every other direct Company-owned table in this schema — Vendor/Document/Invitation all `CASCADE`) — an audit trail must never disappear as a side effect of an ordinary Company deletion; a future full-tenant-deletion workflow, if ever built, must explicitly purge or archive `AuditEvent` rows itself as a deliberate step, never implicitly via this FK. **Human-readable event data, not raw diffs**: Work Order assignment before/after are `{membershipId, name} | null` snapshots (never requiring a live User lookup to render "Unassigned → Mike Johnson"); Property Access changes carry `before`/`after` `{accessMode}` plus `metadata.addedProperties`/`removedProperties` — each `[{id, name}]`, point-in-time Property name snapshots, computed as a true set diff for a restricted→restricted change or the single meaningful explicit-scope list for an All↔Restricted transition (never an exhaustive "every other Property" enumeration); Property archive/restore use semantic `property.archived`/`property.restored` actions with no before/after at all, since the action name alone fully describes the transition. **Data minimization**: Note creation records only `{noteId, authorizationPath}` — never the note's body; the append-only `WorkOrderNote` itself remains the durable source of what was written, and the audit event only ever answers who/when/where. Cost Entry creation records the structured, non-free-text fields (`costEntryId`, `type`, `amount`, `costDate`, `vendorId`/`vendorName`) but never the entry's own free-text `note` or Vendor contact details beyond its name. No call site ever passes a raw request body to `recordAuditEvent`. **Append-only through normal application behavior**: no update route, no delete route, no archive route exists for `AuditEvent` anywhere in this app, and the model itself has no `updatedAt` column — an audit row is never touched again after it's written. This is an application-level guarantee, not a cryptographic or database-privilege one: **a sufficiently privileged database operator could still alter rows directly**; stronger tamper-evidence, external/WORM archival, and database-privilege hardening remain explicitly future work. **No retention policy exists yet** — rows accumulate indefinitely in V1; retention/deletion is an explicit future operations decision, not an oversight. **Read access**: a new, dedicated `auditLog.read` capability (`AUDIT_LOG_READ`), deliberately **not** a reuse of `users.manage` or `settings.access` — Admin/Owner-only in V1, with Manager and Technician denied entirely; a future entity-scoped operational history view may use different, broader authorization rules, but that is explicitly separate from this generalized log. `GET /api/audit-events` resolves its Company context explicitly-but-validated — an optional `companyId` query param, defaulting to the caller's first Company (preserving today's single-Company-per-session UX for free), but always re-checked against `req.companyIds.includes(...)` (the same pattern `createProperty` already established) — never an unchecked `req.companyIds[0]` assumption baked into the security model itself, so a future multi-Company switcher needs no security rework. Pagination is deterministic keyset/cursor (`(created_at, id)`, newest first — never offset, which can duplicate or skip rows under concurrent inserts on a growing table), default limit 50, hard server-enforced max 100 regardless of what a client requests. Optional filters: `action`, `entityType`, `entityId`, `propertyId`, `actorMembershipId`, `from`/`to`. **Frontend**: Settings → Audit Log, gated on `AUDIT_LOG_READ` exactly like every other Settings section gates its own capability — a single dense activity table (Time / Activity / Property), not a database viewer: canonical action keys like `work_order.status_changed` are never shown to a user, translated instead through one centralized `client/src/utils/auditEvents.js#AUDIT_EVENT_CONFIG` map (one entry per action: category, human label, a sentence formatter, and a before/after detail formatter) rather than switch/case formatting scattered across components, so a future V2 event is a one-entry addition. Filters: category (which maps 1:1 to `entityType` — "Work Orders"/"Access & Roles"/"Properties" are just the human names for `work_order`/`membership`/`property`, not a second taxonomy), Property, Actor, and a simple date range. Clicking a row opens a plain modal (the same shell `CreateVendorModal`/`CreateWorkOrderModal` already use) showing only human-readable fields — time, actor, actor role, target, Property, authorization path where relevant, and the before/after detail line — deliberately **no raw JSON blob**; a developer/debug payload view is out of scope for V1.

**Roadmap — real parts of the intended graph, not yet built. Do not treat these as implemented:**

- **Automated invitation email delivery.** Invitation links are copy/paste only in V1 — no SendGrid/Postmark/etc. integration exists.
- **Ownership transfer, Regional Manager role, Property Manager-specific access, a Leasing Agent role, a Maintenance Supervisor role, custom/configurable roles, or a configurable permission matrix.** None of these exist. The ROLE → CAPABILITY architecture is deliberately structured so each can be added later without redesigning it.
- **Organization fields beyond name** (logo, timezone, notification policy, storage configuration, integrations). None have any consuming feature in this app yet; adding them now would be filler, not foundation — see the Settings audit this milestone was based on.
- **Audit V2 — broader mutation coverage.** V1's `AuditEvent` architecture (above) deliberately instruments only eight explicit, high-value events. Asset/Location/Vendor/Document/Site Plan mutations, general Work Order scalar edits (title, description, priority, due date, category, Location/Asset/Vendor reassignment), Work Order archive, and Company rename are all real mutations with no audit trail yet — each is a candidate for its own explicit `recordAuditEvent` call at its existing controller mutation point, following the same pattern, not a new architecture.
- **Audit retention, export, and stronger tamper-evidence.** V1 has no retention/deletion policy (rows accumulate indefinitely), no export/reporting tooling, and no cryptographic tamper-evidence or external/WORM archival beyond "no application update/delete route exists." All three are real future SOC 2/operations decisions, deliberately deferred rather than built speculatively.
- **Property-Access-scoped and entity-level audit reads.** V1's `GET /api/audit-events` is Admin/Owner-only; a Manager-visible, Property-Access-filtered view (reusing the `propertyId` column already indexed for exactly this) and a per-entity "history" panel on Work Order/Property Detail (reusing the `entityType`+`entityId` index already in place) are both natural, low-cost extensions once there's a concrete product need for either.

- **Point / line / polygon geometry.** The Site Plan today supports only point positions (a Work Order's `mapX`/`mapY`). Lines (water/sewer/electrical runs) and polygons (parcels, zones) don't exist.
- **Infrastructure layers** — toggleable Water/Sewer/Electrical/Roads/etc. overlays.
- **Infrastructure service relationships** — e.g. which lots a given valve or line actually serves.
- **Estimate vs. actual cost.** Every cost entry recorded today is treated as an actual, incurred amount; there is no "estimated" or "quoted" state.
- **Location cost history.** An Asset now has a derived lifetime-cost view (see above); a Location does not yet have the equivalent rollup.
- **Broader Reports** — spend by Location, spend by Asset, cost trends over time, recurring-problem / repeat-failure detection.
- **Exports** — CSV/PDF/Excel.
- **Document attachment to Location**, and Document features such as OCR, AI extraction/summaries, e-signatures, approvals, external sharing, version control, expiration/COI tracking, or a vendor-facing portal. Document V1 intentionally covers Property/Asset/Work Order/Vendor attachment only.

## Core Experience

Five pillars, each answering one question:

| Pillar | Question it answers |
|---|---|
| **Operations** | "What needs attention right now?" |
| **Property** | "What's happening at this property?" |
| **Map** | "Where is it physically, and what does it affect?" |
| **Work Order / Asset** | "What exactly is happening, and what are we doing about it?" |
| **Reports** | "What keeps happening, what are the trends, and what is it costing?" |

## UX North Star

- **Regional Manager** — understand portfolio health in 30 seconds.
- **Property Manager** — understand what's wrong at a property in 15 seconds.
- **Technician** — understand what to do next in 5 seconds.
- **Operator / Owner** — answer cost/performance questions without needing Excel.

## Design Principles

- Powerful without being complicated.
- Operational without being cluttered.
- Visual without being decorative.
- Intelligent without hiding facts.
- Manufactured-housing first without being manufactured-housing locked.
- Avoid generic SaaS card soup.

Prefer:
- Strong information hierarchy
- Progressive disclosure
- Persistent context
- Restrained attention colors
- Useful information density
- Clear typography
- Obvious next actions
- Spatial context where useful

The Dashboard is a **management morning briefing**, not a widget collection. Reports should answer business questions through drill-down rather than forcing users to export to Excel. Map will eventually be a flagship operational site-plan experience supporting Locations, Assets, Work Orders, configurable infrastructure layers, points, lines, polygons, and future service-impact relationships.

## Guiding Principle (carried forward from Version 1.0)

Every feature we build must answer one question: **does this help our customer make a better decision?** If the answer is no, it doesn't belong in the product.

# Version 1.0 (Historical / Superseded)

The following is the original Version 1.0 document, preserved for historical context and because much of its product-level detail (asset fields, work order fields, vendor/document model, roadmap) remains useful and has not been re-specified under 2.0. **Where this section conflicts with Version 2.0 above — primary beachhead market, and the exact framing of the core experience/navigation model — Version 2.0 governs.**

### Vision

Build the operating system for property maintenance and asset intelligence.

We are not building another property management software like Entrata, AppFolio, or Yardi. We are building the software owners, regional managers, maintenance directors, and property managers open every morning to understand the health of every property they own.

### Mission

Give every physical asset on a property a complete digital history. Help property management companies make better maintenance and capital investment decisions.

### Core Philosophy

If it exists on a property, we should be able to map it, track it, and know its story.

### Version 1.0 Goal

Create one central place where property management companies can:

- Visually see every property
- Track every asset
- Manage every repair
- Store every document
- Know every dollar spent

No forecasting. No AI. No accounting. Just an incredible foundation.

### Target Customers (as originally framed — see Primary Beachhead above for the current framing)

Primary: Property Management Companies, Regional Maintenance Managers, Maintenance Directors, Property Managers.

Future: Mobile Home Parks, HOAs, Hotels, Commercial Properties, Self Storage, Universities, Hospitals.

### Core Product

**1. Dashboard** — Simple portfolio overview. Shows Properties, Open Work Orders, Recent Activity, Assets Requiring Attention, Maintenance Spend, Quick Search.

**2. Portfolio** — Shows every property owned. Searchable. Filterable.

**3. Property Page** — Every property has two ways to navigate:

*Map View* — Visual. Satellite image or uploaded site map. User clicks: Property → Building/Lot → Unit (if applicable) → Asset.

*List View* — The same information, displayed like Excel. Sortable, filterable, exportable, saved views, bulk edit, reports.

**Why two views?** Map View answers "where is it?" — visual understanding, find assets quickly, see problem areas. List View answers "tell me everything" — spreadsheet, filtering, sorting, reporting, bulk editing, exporting. The Map and List always stay synchronized.

### Property Structure

The software should NOT be apartment specific. Everything is built around locations:

```
Portfolio → Property → Location → Sub Location (optional) → Asset
```

Examples:
- Apartment: Property → Building → Unit → Asset
- Trailer Park: Property → Lot → Asset
- Hotel: Property → Floor → Room → Asset
- Commercial: Property → Suite → Asset

This allows support for many industries without changing the software.

### Assets

Every asset has its own profile. Examples: Water Heater, HVAC, Roof, Refrigerator, Dishwasher, Washer, Dryer, Parking Lot, Sidewalk, Pool Pump, Irrigation Controller, Trees, Street Lights, Fire Systems, Mailboxes — anything.

Each asset stores: Install Date, Purchase Price, Vendor, Manufacturer, Model Number, Serial Number, Warranty, Expected Life, Photos, Invoices, Manuals, Repair History, Lifetime Cost, Notes. **Version 2.0 correction:** "Lifetime Cost" and "Repair History" are superseded by the governing principle above — an Asset's maintenance history and lifetime spend are always derived live from its real Work Orders and Cost Entries, never stored as separate fields on the Asset itself.

Every asset becomes its own timeline.

### Work Orders

Simple statuses: Open, Assigned, Waiting, Completed.

Every work order belongs to: Property → Location → Asset.

Stores: Labor, Material Cost, Vendor, Photos, Documents, Notes, Completion Date.

### Vendors

Every vendor gets their own profile. Includes: Contact Information, Insurance, Licenses, Work Orders, Invoices, Lifetime Spend, Properties Served.

### Documents

Every asset and work order can store: Photos, Warranties, Manuals, Invoices, Receipts, Inspection Reports, Permits.

### Global Search

Find anything instantly: Property, Asset, Vendor, Serial Number, Model Number, Invoice, Work Order, Warranty, Documents.

### Layer System (Map)

The map can toggle layers. Examples: Buildings, Units, Water, Sewer, Electrical, Gas, HVAC, Roofs, Parking Lots, Trees, Fire Systems, Irrigation, Utilities. Future layers can easily be added.

### Things NOT Included in Version 1

No AI, No Budget Forecasting, No Accounting, No QuickBooks, No Insurance, No Predictive Maintenance, No Capital Planning, No Resident Portal, No Leasing, No Payments, No Inventory, No Vendor Ratings, No Portfolio Intelligence.

Why? Version 1 is about collecting clean, structured, trustworthy data. Without great data, AI is useless.

### Long-Term Roadmap

**Version 2** — Professional Reports, Excel Export, PDF Reports, Scheduled Reports, Portfolio Reporting.

**Version 3** — AI Assistant ("What happened this month?", "Summarize Building 4.", "Show my most expensive assets.").

**Version 4** — Predictive Maintenance, Asset Health Scores, Warranty Alerts, Expected Failures, Replacement Suggestions.

**Version 5** — Capital Planning, 5-Year Budgets, "What If" Scenarios, Capital Forecasts, Replacement Planning.

**Version 6** — Portfolio Intelligence, Cross-property benchmarking, Vendor performance analytics, Regional dashboards, Executive reporting, AI financial planning.

### Future Vision

Become the Bloomberg Terminal for property maintenance. Not the software that stores maintenance records — the software executives use to answer:

- Where is my money going?
- What should I replace next year?
- Which assets are costing me the most?
- Which vendors are performing the best?
- What should my capital budget be?

### Guiding Principle

Every feature we build must answer one question: does this help our customer make a better decision? If the answer is no, it doesn't belong in the product.

I genuinely think this is our north star now. If we stay disciplined and build this before chasing AI, we'll have a foundation that can grow into something much bigger than a maintenance tracker. AI should become the amplifier of great data — not the product itself.
